01

项目要解决的问题：题要有区分度

评测的目的是比较两个配置的强弱。一道所有配置都能过、或所有配置都过不了的题， 跑多少次都产生不了这个信息。

这不是抽象顾虑。让模型自己编题，产出的难度分布是这样的 （auto-v0 126 条，三锚点面板实测）：

六成是送分题，两成多是无人能解的题，真正落在中档的只有 13.5%。 校准跑一遍的成本是「锚点数 × 重复次数」次全量跑测， 花掉这笔钱之后，126 条里只有 28 条被判为有区分度。 所以这个模块要解决的第一件事，是怎么把题造得有区分度。

它在 Agentic Scaling 里的位置

上层设计要求所有领域 benchmark 共用一套结果表口径： 一行 = 同一 benchmark + 同一 case 集 + 一个算法配置 + 一个预算档 + 一次 run。 本模块是领域 benchmark AI-Coding-Assist 的执行与填表实现， 不是设计，也不是算法本身。

02

反向构造：缺陷交给真人，模型只写测试

模型无论拿到什么输入，编出来的都是同一种难度。 那就不让模型决定缺陷是什么。

一条真实会话里，工程师对某个文件做过若干次 edit。 按时间顺序重放这些编辑，可以还原出该文件修改前与修改后两个版本。 这两个版本分别成为用例的两端：

trace 里的东西在用例里的角色字段
编辑前的文件内容待修复代码（stub）context.files[].content
编辑后的文件内容参考解grader.gold_files
模型写的测试判分依据，部分转为隐藏测试grader.hidden_tests
模型写的题面只描述症状，不提机制prompt

这个设计自带验证，不需要新机制

两道既有门禁就能验证模型交出来的东西：check_stub_fails 要求测试在 stub 上失败， check_reference_solution 要求它们在参考解上通过。 写不出能区分两版的测试，用例就被现有门禁拒掉。 所以模型没有能力把题变简单，只可能描述失败。

src/aibench/validity.py

"""Build a case whose defect is the one an engineer actually made.

Ordinary generation asks a model to invent a benchmark case, and it answers with a two-file,
thirty-line exercise no matter what it was given. Here the defect is not up for negotiation:
the stub is the file as the trace found it, the reference solution is the file as the trace
left it, and the model's only job is to write tests that tell the two apart.

That job is verifiable without any new machinery. ``check_stub_fails`` already requires the
tests to fail on the stub and ``check_reference_solution`` requires them to pass on the gold,
so a model that writes tests which do not separate the two versions produces a case the
existing gates reject. The model cannot make the task easier, only fail to describe it.
"""

src/aibench/extract/reverse_case.py 的模块注释，逐字引用

一个必须补的门禁

源码文本天生能区分两版，因为修复改动的就是文本。 一条形如 assert.match(source, /async function prepareReview/) 的测试， 在 stub 上必失败、在参考解上必通过，两道门禁按构造 100% 通过， 而它评的是抄写不是行为。所以另有一道 test_reads_source_text 专门拦这种测试，见 09 效度门禁。

重放采用严格顺序匹配

只在会话确实读取过的内容上应用编辑，并严格按消息顺序推进。 宽松匹配（在 trace 的任意快照里搜旧串）重建率高得多， 但一次匹配到错误版本就会重建出一个从未存在过的中间状态， 用例便成了带着真实代码的虚构。这里选严格匹配。

配套的是一条来源阶梯：pre 只接受 read_complete 这一种来源。 写回的内容（tool_write）不能证明是读到的，未标注来源的读取（read_unlabelled） 同样不可信，两者全部被拒。

src/aibench/extract/file_versions.py

代价是产率低。extract-from-db --require-usable-pair 用的正是 generate-cases --reverse 的那条判据，草稿池里合格的约占 1.5%， 绝大多数草稿根本没有 pre/post 对。抽库时要按这个比例给预算。

docs/REFERENCE.md §8.5

去重键是（stub，参考解），不是用例指纹

同一个会话的不同 trace 行会重放同一次编辑。模型每次写不同的题面和不同的测试， 于是每个副本都拿到不同的 case_fingerprint，duplicate_fingerprint 什么也看不见。 而冗余副本同时抬高 n 又让配对结果相关，正是本项目头条统计量（配对 McNemar）假设不存在的那件事。

所以去重走 solution_key：只哈希 role=impl 的文件与 gold_files 的 (path, content)，刻意排除题面与测试。 没有 stub 或没有参考解时返回 None，调用方当「无法去重」处理， 绝不当「没有重复」。

追一条 case：从 JSON 文件到 results.jsonl 的一行

这一节按调用顺序走，不按目录顺序走。看懂这条线就看懂了 run 与 ablation 和 calibrate-cases 的公共部分，后两者都在内部调 run_benchmark。

第 1 步：run_benchmark 装配三份配置

三层配置在这里合流：run 配置给预算与默认值，agent 与 model 配置可被 CLI 覆盖。 相对路径一律相对仓库根解析。 

run_cfg  = RunConfig.from_dict(load_yaml(run_config_path or configs/runs/baseline.yaml))
agent_cfg = AgentConfig.from_dict(load_yaml(--agent 或 run_cfg.agent_config_path))
model_cfg = ModelConfig.from_dict(load_yaml(--model 或 run_cfg.model_config_path))
cases     = load_cases(case_set, validate=True)      # schema 校验在这里做

src/aibench/runner.py

模型名以模型 YAML 的 model 字段为准，OPENAI_MODEL 只在该字段为空时兜底。 这条优先级不是风格问题：反过来的话，多模型消融会静默跑成同一个模型。

第 2 步：开跑前的三道拦截

检查不过会怎样为什么放在开跑前
selection_strategy 是否已知抛 ValueError 写错的策略名必须显式失败，否则 manifest 记着一个并没有被执行的策略名
JS/TS 用例与 node 版本打印告警，逐条记 infra_error 拒整个 run 会让「100 条 Python 里混 1 条 TS」的集合在能跑 100 条的机器上不可用
expected_case_set_fingerprint抛 RuntimeError 拒跑 集合内容会随重新生成而漂移，指纹保证这次的数字被归到它真正对应的集合上

src/aibench/runner.py

以 . 开头的派生子集（.ablation-filtered-*、.calibrating-*） 跳过指纹比对：它们按定义就是子集，指纹不可能等于母集。

第 3 步：parallel_map 按 case 并行

并行度取 --workers，否则取 run 配置的 case_workers（生产 baseline 是 4）。 每条 case 拿到独立的工作区目录与独立的 Agent 实例。 并行不改变单 case 语义，这条由测试锁住。

src/aibench/parallel_util.pytests/test_stats_parallel.py

第 4 步：_run_one_attempt 是真正干活的那 154 行

顺序固定，每一步的异常都被包住：

  1. materialize_workspace() 建工作区，写 workspace_manifest.json；失败即 infra_error，不进 Agent。
  2. workspace_inventory(workspace) 取开跑前清单。这一步在 Agent 跑之前， 是后面判分干扰检测唯一的依据。没有它就分不清「用例自带的文件」和「提交里新加的文件」。
  3. create_agent(agent_cfg, model_cfg).run(case, workspace, max_steps, max_wall_time_s)。
  4. grade_case(case, workspace, baseline=baseline)。
  5. 组装结果行并返回。cases/<case_id>/result.json 由外层的 _run_one_case（runner.py）写出。

src/aibench/runner.py

这五步全部包在 try 里，异常一律折成 GradeResult(infra_error=True)。 parallel_map 会把 worker 里逃出来的异常重新抛给执行器， 所以只要有一步没被包住，一条 case 就能在其余 case 都已付费跑完之后带走整个 run 的产物。

第 5 步：case 级重试只覆盖基础设施失败

统计口径：为什么用配对检验而不是各自的置信区间

stats.py 全部是估计量。其中 item_rest_correlation 决定哪些用例被保留。

Wilson 区间用于单个成功率

center = (phat + z2 / (2 * n)) / (1 + z2 / n)
margin = (z / (1 + z2 / n)) * sqrt(phat * (1 - phat) / n + z2 / (4 * n * n))

写成数学式。源码把 1 + z2 / n 提成了 denom，见 src/aibench/stats.py

小样本下比正态近似可靠，且在 phat = 0 或 1 时不退化成零宽区间。 n = 0 返回 None，不返回 (0, 0)。

比较两个配置用精确 McNemar

n = b + c                                    # 只有结论不同的 case 携带信息
k = min(b, c)
tail = sum(math.comb(n, i) for i in range(k + 1)) * (0.5 ** n)
p = min(1.0, 2.0 * tail)

src/aibench/stats.py

b 是仅 A 解出的用例数，c 是仅 B 解出的。 两者都通过或都失败的用例不携带「谁更强」的信息，按构造被排除。

这就是它比 Wilson 灵敏的原因

两组跑的是同一个 case 集，属于配对数据。各自算独立区间会丢掉配对信息： 56/64 与 62/64 的 Wilson 区间大幅重叠、看起来「无差异」， 而配对检验在 6 个不一致 case 上给出 p ≈ 0.03，判定显著。

反推题量：题量由不一致率决定，不是拍脑袋

n = (z_α·√ψ + z_β·√(ψ − δ²))² / δ²        # ψ = 不一致率，δ = 要检出的成功率差

数学式。源码写作 ((z_a * math.sqrt(discordance) + z_b * math.sqrt(discordance - delta**2)) ** 2) / (delta**2)

src/aibench/stats.py

参数校验里有一条：discordance 必须大于 delta， 否则报错「两个 run 的差异不可能超过它们的不一致程度」。

observed_discordance 只统计跨配置的配对，排除同一配置的重复运行。 自重复的不一致率显著低于跨配置（实测 4.8% 对 14.9%）， 而 required_cases 随 ψ 单调上升，混进自重复会让规划出的题量比真实需要的更少。 全是自重复时返回 None，不回退到全量列表。

成本轴：档位由数据分位数产生

cost_curve 是若干 token 预算档位上「在该预算内解出的 case 数 / 有效 case 数」。 档位由该 run 的 per-case token 分布分位数产生（budget_quantiles），不是人工拍板。 跨配置比较时必须用同一组档位，否则每条曲线各有各的 x 轴。

src/aibench/stats.py

消融报告另给 token_amplification：准确率提升若是用 5 倍 token 买来的， 和等成本下的同等提升不是同一个结论。

限制现状方向
样本量 可用集合规模在几十条量级。按实测不一致率反推， 消融要达到既定检验效能需 150 条以上，具体模型对需要 60 到 350 条不等 继续抽取与校准；用 aibench plan-sample-size --delta 10 --from-ablation <ablation_summary.json> 定题量
语言覆盖 只有 Python 与 JavaScript / TypeScript 能生成并评分，这是产率的首要上限。 可重建的文件版本里，因语言未注册而丢弃的量约为可用量的 20 倍 阻塞点不是一份语言规格，是工作区模型： 编译型语言需要头文件、构建描述与依赖闭包，且失败从导入期移到编译期。 优先级最高的是先做依赖闭包
难档 「无人能解」这一档目前造不出来。 最强锚点在多数用例上三次全过，p_hat 的下限被钉在 1/3，进不了难档 输入特征（编辑次数、改动行数、文件行数）均被验证无效； 起作用的是任务形态，目前只有隐藏测试一条路

  • 模型比较至少 3 次重复，并报轮间极差。 同一模型的轮间波动可以与模型之间的差距同量级，单次运行得出的显著性不可信。

  • 判分命令在宿主机执行，用例集要来源可信。见 08。
  • node 固定 24（.nvmrc）。 低于 22.18 时 node --test 发现不了 TypeScript 测试却退出 0，会被判为通过。
  • uv sync 要同时带 --extra dev --extra grading。 只带 dev 会卸掉 grading extra，测试会红。
  • 指纹版本前缀是有意的破坏性变更。 升级 v3: / v2: 后所有既有校准不再可复用，这是正确行为。
